## 一、[已修] Welcome home 死循环 —— 功能对老用户完全锁死

**现象**：Joe 进 Roam 直接跳到「宠物回家了」界面，发不出新漂流；点 Welcome home
之后闪一下又弹回同一个界面，无限循环。

**根因**：`travel_posts.status` 的 CHECK 只有 `('traveling','returned')`，
**没有任何值表示「这趟旅行已确认收工」**。于是：

```ts
welcomePetHome()      → update status='returned'   // 它本来就是 'returned'，等于什么都没做
getActiveTravelPost() → .in('status',['traveling','returned'])  // 又把同一条查出来
```

`FreeTravelScreen` 点完只是本地 `setActivePost(null)` 闪一下，下次进页面又被拉回去。

**影响范围**：Joe 那条 2026-08-07 的帖子卡在「等待迎接」**整整 7 天**，期间发不出任何漂流。

**修复**：迁移 69 加 `welcomed_at timestamptz` 作为终态 + 历史数据一次性归档；
客户端 `welcomePetHome` 写时间戳、`getActiveTravelPost` 加 `.is('welcomed_at', null)`。
纯增量，没改 CHECK / RLS / `match_travel_posts`。
回滚：`db-backups/2026-08-14/ROLLBACK_69.sql`（⚠️ 会删列）

**验证**：Joe 真机重进 Roam → 显示「Ready to Roam」发布表单 ✅

## 三、[已修] 发现页几乎无法抵达

**问题**：`NearbyTravelScreen`（刷别人漂流瓶的页面）**全 App 只有一个入口**：

```tsx
// FreeTravelScreen 的返回箭头
onPress={() => {
  if (activePost && new Date() < new Date(activePost.ends_at)) {
    navigation.navigate('NearbyTravel');   // ← 唯一入口
  } else {
    navigation.goBack();
  }
}}
```

两个毛病：

1. **必须自己的宠物正在旅行才能进**
2. **入口是返回箭头** —— 没有用户会猜到「返回」会跳进一个发现流，点它的人本意是退出

**修复**（Joe 定的交互：进 Roam 后就是两个选项 —— 看别人 / 发自己）：

- `FreeTravelScreen` 顶部新增常驻的 **Browse Roamers** 卡片，
  三种状态（未出发 / 旅行中 / 已归来）下都可见
- 返回箭头恢复成单纯的 `goBack()`
- 反方向的回链本来就有：发现页空状态的「Send My zZuPer」→ 发布页

**产品决策**：看别人**无条件可用**，不要求自己的宠物先出发（Joe 拍板）。
原实现那种"先发才能看"的互惠门槛对冷启动不利 —— 新用户第一次进来只会看到空白。

## 四、[Ethan] 匹配拿「我是谁」去匹「别人写了什么」

**实测数据**（这是本次最硬的一条证据）：

```
Joe 的帖子    "Claude can you see it"
Claude 的查询向量（由 profile 拼成）
余弦相似度    0.1113
match_threshold  0.2
→ 没过门槛，直接被过滤，界面显示 "All Quiet Nearby..."
```

**根因在查询向量的构造方式**（`travel-mode` 函数 action:'match'）：

```ts
const queryText = `University: ${university}. Bio: ${bio}. Pet Bio: ${petBio}.
                   Pet Name: ${petName}. Interests: college life, study, food, social, play.`
```

它用**用户档案**去匹配**帖子内容** —— 两边根本不是同一类文本，天然低相似度。

而 Claude 的 profile 几乎是空的（`university/bio/pet_bio` 全 null），实际查询文本退化成：

```
University: . Bio: . Pet Bio: . Pet Name: Zorp. Interests: college life, study, food, social, play.
```

**一句写死的兴趣模板 + 一个宠物名。** 用它匹配任何真实内容，相似度都低得可怜。

**叠加效应**：profile 越空 → 查询向量越接近那句固定模板 → 越匹配不上 →
**新用户几乎刷不到任何人**。而新用户恰恰是最需要看到内容的人。

> ⚠️ **更正我在 PULSE 记录第八条里的判断**：我当时说「0.2 阈值形同虚设、几乎总是通过」。
> **这个结论是错的**，被本次实测推翻 —— 两段无关短文本的真实相似度只有 0.11，远低于 0.2。
> 阈值是实打实在拦人的。

## 五、[Ethan] 注释承诺的兜底没有实现

```ts
match_threshold: 0.2, // Low threshold to allow random diffusion fallback
```

注释说"低门槛以允许**随机扩散兜底**"，但 `match_travel_posts` 里**没有任何兜底分支** ——
过不了门槛就是空列表，没有"实在没有就随机给几条"的逻辑。

**对比 Pulse 那边**：`try_match_user` **有**兜底（没有超阈值候选就配等最久的，完全不看相似度）。
Roam 缺了对应的一层。

## 六、事实记录：Roam 从未有过一次成功闭环

```
travel_posts     累计 3 条（含本次测试的 2 条）
travel_comments  0
travel_post_views 0
```

之前推测是"没人用"。现在看更可能是 **用了也刷不到** —— 第一条（8/7）之后就被
Welcome home 死循环锁死，而即使发出去了，匹配也过不了门槛。

**这三条是叠加的**：死循环挡住发布 → 匹配门槛挡住发现 → 没人能留言 → 没有数据 →
看起来像"功能没人用"。

## 七、待验证：算法坏了，还是冷启动数据太空？

本次测试双方 profile 都近乎空白（无 bio、无 pet_bio、无学校），
无法区分是**匹配设计有问题**还是**只是数据太少**。

下一步建议：两边都把 `bio` / `pet_bio` / `university` 填实，写一条真实语义的漂流内容，
再测一次。如果那时能刷到，说明算法在资料完整时可用，问题只在冷启动；
如果仍刷不到，则是查询向量的构造方式需要重做（例如改成用**帖子内容**互相匹配，
而不是用档案匹配内容）。
