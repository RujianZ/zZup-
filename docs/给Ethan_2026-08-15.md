## 一、我的改动对你那边的影响（需要你知道）

### 1. `is_agent_chat` 现在会在加好友后被清掉

迁移 87：`handle_friendship_update` 升级会话时，除了
`is_temporary=false, kind='dm', expires_at=null`，现在还会 `is_agent_chat=false`。

**对你的直接影响**：`trigger_agent_chat_reply` 第一句是

```sql
if v_is_agent_chat is not true then return new; end if;
```

所以**加完好友之后 AI 就彻底不再替谁说话了**。原来只有「双方都接管过」
（各自发过 identity_mode='real' 的消息）才停得下来，光加好友是停不住的。

**你的函数一个字没改**，这是数据变准带来的结果。我判断加完好友双方就是真人对话、
代理没有存在理由，所以是对的 —— 但如果你那边的设计里加好友之后 AI 还该说话，
告诉我，我改回去。

### 2. `profiles` 的读权限已经撤销

`authenticated` 现在只有 `select (id)`，其余列一列都读不到；RLS 策略也收成
「只看自己那一行」。

- **Edge Function 用 service_role 的不受影响**（agent-chat / pet-chat / travel-mode 都是）
- 但如果哪里用 anon/authenticated key 去读 profiles，会静默拿到空或者 42501
- 要读别人的资料请走 RPC：`get_other_profile` / `get_pet_identity` /
  `conversation_peer_profile`

### 3. 宠物身份的消息，`sender_id` 对客户端恒为 `null`

迁移 77：`list_messages` / `get_message` 对 `identity_mode='pet'` 的消息
不返回 `sender_id`，改返回服务端算好的 `is_mine` 和一个会话内代号（如 "A Time Lord"）。

**数据库里的 `messages.sender_id` 没有变**，你的函数照常读。这只影响客户端读取路径。

## 三、待确认的设计问题（不算 bug，但想跟你对一下）

### 1. Roam 的「已看过」抑制是在**匹配时**记录的，不是打开时

`match_travel_posts` 里：

```sql
AND NOT EXISTS (
  SELECT 1 FROM travel_post_views tpv
  WHERE tpv.travel_post_id = tp.id AND tpv.user_id = p_user_id
)
```

实测：Joe 03:47:08 发帖，**03:47:20 就被记成 Claude「看过」了** ——
中间没有人点过那张卡片（客户端的 `recordTravelPostView` 绑在 `handleCardPress` 上）。
所以记这一笔的只可能是 travel-mode 的 match 分支本身。

结果是「**匹配到 = 永久消费掉**」：列表刷出来那一刻就算看过，用户还没点进去、
甚至可能没滚动到它，它就再也不会出现了。Roam 帖子有 6 小时窗口，
这意味着一个帖子对每个人只有一次露面机会。

如果这是有意的（防止同一批帖子反复刷屏），那也许该记在**点进详情**的时候，
而不是列表返回的时候。

### 2. Pulse 在 30 秒内给同一对人匹配了两次

| 会话 | 创建时间 |
|---|---|
| `44620379-8e30-4020-9c91-23168e0e6418` | 03:39:40 |
| `a89371f0-4336-4ba5-b3a0-ee964737b174` | 03:40:10 |

同一对用户（joe / Claude），两个会话内容一模一样，都只有那条开场白。
`try_match_user` 那边可能缺一个「这两人当前已有活跃临时会话就不再匹配」的判断。

### 3. 已经是好友的两个人，仍然会在 Pulse / Roam 互相匹配

`try_match_user` 和 `match_travel_posts` 里都没有排除已有好友关系的条件。

⚠️ **这条是读源码得出的，没有实测验证过** —— 之前一次看起来像的复现，
事后确认是测试前已经解除好友了，所以不算证据。
