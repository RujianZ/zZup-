## 1. ✅ 年龄门槛（2026-08-15 已完成）

### 实际做出来的东西

**服务端（权威）** —— `supabase/migrations/75_age_gate.sql`

`profiles` 的 BEFORE INSERT OR UPDATE OF `date_of_birth` 触发器。五个边界已实测：

| 输入 | 结果 |
|---|---|
| 17 岁生日 | 拒绝 ✓ |
| 差一天满 18 | 拒绝 ✓ |
| 刚好满 18 岁整 | 放行 ✓ |
| 未来日期 | 拒绝 ✓ |
| NULL | 放行 ✓（删号会把生日置空，拦了删号就崩） |

**时区一律按美东算**，用命名时区 `America/New_York` 而不是写死 `EST` —— 后者不含夏令时，
3 月到 11 月会差一小时。数据库会话时区是 UTC，直接用 `current_date` 会比美东快最多 5 小时。
恰好卡在生日当天的边界情况极少，不做特殊处理。

**客户端** —— `OnboardingScreen.tsx`

自由文本框换成 `@react-native-community/datetimepicker` 日历，
`maximumDate` = 美东今天减 18 年，**未成年的日期根本选不中**（防止而非事后报错）。
默认值设成「刚好满 18 岁」那天，18 岁用户一下确认，年长的往回滚。
客户端也按美东算（`Intl.DateTimeFormat` + `America/New_York`），不跟随设备时区——
设备时区可随手改，跟着走等于给了个绕过门槛的旋钮。

### 关于「用户可以谎报生日」

管不了，也不需要管。Apple 指南和 COPPA 要求的是**中立的年龄声明门槛**
（neutral age gate），不是身份核验。行业标准做法就是这样。

回滚：`db-backups/2026-08-15/ROLLBACK_75.sql`

### 要做什么

**服务端（权威，客户端绕不过）**

新建迁移 `71_age_gate.sql`：

```sql
-- profiles 的 BEFORE INSERT OR UPDATE 触发器
-- date_of_birth 非空时，拒绝不满 18 周岁的写入
create or replace function public.enforce_minimum_age()
returns trigger language plpgsql as $$
begin
  if new.date_of_birth is not null
     and new.date_of_birth > (current_date - interval '18 years') then
    raise exception 'You must be at least 18 to use zZuP!'
      using errcode = '23514';
  end if;
  return new;
end;
$$;

create trigger trg_enforce_minimum_age
  before insert or update of date_of_birth on public.profiles
  for each row execute function public.enforce_minimum_age();
```

### ⚠️ 两处**故意偏离**本文档原方案，明天讨论时按实际的来

## 3. 🔴 pet_memories 不可查看、不随删号清除

### 现状

这是整套合规里**最难解释**的一条。

`pet-chat` 每次对话后会异步跑一次额外的 LLM 调用，把用户说的话里的个人事实抽出来存库：

- 表定义：`supabase/migrations/56_pet_companion.sql:15` ——
  `pet_memories(id, user_id, summary, embedding, created_at)`
- 写入逻辑：`supabase/functions/pet-chat/index.ts:143-176`
- 存的内容长这样：`"Owner loves eating ramen"`、`"Owner is studying Computer Science"`

**这是一份由机器自动生成的用户画像，是不折不扣的个人信息。** 但是：

1. **没有任何界面能查看或删除它** —— 用户不知道宠物"记住"了什么，也没法纠正记错的内容
2. **`delete_my_account`（迁移 67）根本没碰这张表**。因为 profiles 是**软删除**，
   `pet_memories.user_id → profiles(id) ON DELETE CASCADE` 这条级联**永远不会触发**。
   结果：**用户删号之后，AI 写下的关于他的个人事实永久留存**
3. 同样的问题也存在于 `pet_chat_messages`（迁移 67 的注释里写了"删除策略待 Ethan 确认"）

隐私政策里我已经写明"你可以读取和删除宠物记忆"，`terms.html` 也这么写了 —— **目前这是假的。**

### 要做什么

**（a）纳入删号清理** —— 新建迁移 `73_delete_pet_data.sql`，或直接改 `delete_my_account`：

```sql
-- 在 delete_my_account 的第 1 层（抹除个人识别信息）之后加：
delete from public.pet_memories     where user_id = v_uid;
delete from public.pet_chat_messages where user_id = v_uid;
```

理由：这两张表**只对用户自己有意义**，不像 `messages` 那样属于对话双方，
也不构成任何举证价值（同样内容在 `messages` 里另有一份）。没有任何保留它们的正当理由。

**（b）查看 / 删除界面**

在 Profile 里加一个「你的宠物记得什么」页：

- 列出 `pet_memories.summary`，按时间倒序
- 每条可单独删除
- 一个"全部忘记"按钮
- 空状态文案要诚实：还没有记住任何东西

需要一个 `list_my_pet_memories()` 和 `delete_pet_memory(p_id)` 的 RPC，
或者直接靠现有 RLS（`56` 里的策略已经是 `auth.uid() = user_id` 的 FOR ALL，客户端可直接读写）。

**（c）顺带修一个 bug**

`agent-chat/index.ts` 有两处查 `pet_memories`：

- 第 171-176 行：`.select("memory_text")`
- 第 261 行：`.select("memory_text")`

但表里那一列叫 **`summary`**（见 `56_pet_companion.sql:18`）。这两个 select **必然报错**，
被 `?.` 静默吞成空字符串。也就是说 **Pulse 里"宠物带着主人的记忆去破冰"这个卖点从来没生效过**。
改成 `.select("summary")` 并相应改下面的 `.map((m) => m.memory_text)`。

### 验收标准

- [ ] 删号后 `select count(*) from pet_memories where user_id = '<已删账号>'` 返回 0
- [ ] `pet_chat_messages` 同上
- [ ] Profile 里能看到记忆列表，删除后再问宠物同一件事，它确实不记得了
- [ ] `agent-chat` 的 `memory_text` → `summary` 改完后，Pulse 开场白里能体现主人的记忆

### 法务依据

隐私政策「你的权利」一节承诺了 correct 和 delete，其中特别点名了
"including a pet memory the AI got wrong about you"。美国各州隐私法都有 delete 权，
删号后仍保留机器生成的用户画像**没有任何可援引的豁免**（安全 / 反欺诈 / 法规遵从都套不上）。

## 4. 🟠 app.json 申请了从不使用的后台定位权限

### 现状

`app.json` 里：

```jsonc
"android": {
  "permissions": [
    "android.permission.ACCESS_COARSE_LOCATION",
    "android.permission.ACCESS_FINE_LOCATION",
    "android.permission.ACCESS_BACKGROUND_LOCATION",   // ← 后台定位
    "android.permission.FOREGROUND_SERVICE",
    "android.permission.FOREGROUND_SERVICE_LOCATION"
  ]
},
"plugins": [
  ["expo-location", {
    "locationAlwaysAndWhenInUsePermission": "zZuP! uses your location to show friend locations.",
    "isIosBackgroundLocationEnabled": true,
    "isAndroidBackgroundLocationEnabled": true
  }]
]
```

但是：

- **`expo-location` 全项目零引用**（`grep -r "expo-location" --include=*.ts --include=*.tsx` 无结果）
- 那套地图 / 打卡 / 好友位置的功能在 6 月 v3 重构时**整套删掉了**（`user_locations`、
  `landmarks`、`explorations` 表全清），权限文案里的 "show friend locations" 指的就是这个已删功能
- `expo-notifications` 同样零引用（推送下发未建，见 `DEFERRED.md` #9）

**申请一个从不使用的权限 —— 尤其是后台定位 —— 是 Apple 审核的经典拒绝理由**
（指南 5.1.1：只能请求实现当前功能所必需的数据）。Google Play 对后台定位另有独立的
申报和审核流程，同样会卡住。

### 要做什么

1. 从 `app.json` 删掉整个 `expo-location` plugin 配置块
2. 删掉 android 的五条定位 / 前台服务权限
3. `npm uninstall expo-location expo-notifications`（确认真无引用后）
4. `npx expo prebuild --clean` 或直接重新 EAS Build，确认生成的 manifest 里没有残留

### 验收标准

- [ ] 构建产物的 `AndroidManifest.xml` 里搜不到 `ACCESS_BACKGROUND_LOCATION`
- [ ] iOS 的 `Info.plist` 里没有 `NSLocationAlwaysAndWhenInUseUsageDescription`
- [ ] App 启动和全流程功能不受影响

### 法务依据

隐私政策「What we do not do」一节明写 **"We do not collect your location. The app has no
GPS feature."** 只要 manifest 里还留着后台定位权限，这句话在审核员眼里就是不实陈述。

## 6. 🟡 匿名强度是 A 方案

### 现状

`docs/DEFERRED.md` 第 10 条记录得很清楚：本期采用 **A 方案（API 层去标识化）** ——
库里照常存真实 `account_id`，`messages` / `conversation_members` 对成员开放直查（为了保住
Realtime），去标识化只靠读取 RPC。

弱点也写明了：**绕过 RPC 直查仍暴露 `account_id`，挡不住抓包 / 改客户端**，
无法对抗确定型攻击者跨窗口对照（宠物马甲 ↔ 真人账号）。

### 现在怎么处理的

隐私政策里没有粉饰，「How anonymous your pet actually is」一节按四个层次如实写了：

- 对普通用户：有效
- 对我们自己：完全不匿名（这是屏蔽和审核能成立的前提）
- **对技术攻击者：比看起来弱**，改客户端的人有可能把宠物身份关联回账号
- 对你自己：你说漏嘴了谁也救不了

### 要做什么（二选一）

- **A. 保持现状** —— 那就**一个字都别改**隐私政策里那段。绝不能把当前构建描述成强匿名
- **B. 上线前升级** —— 走 DEFERRED #10 里的 B 方案（纯 RPC 读取，`account_id` 永不出库，
  牺牲直连 Realtime）或 C 方案（每窗口不透明 `member_handle` 列，保住 Realtime）。
  工作量不小，涉及 `messages` / `conversation_members` 的 SELECT 权限、读取 RPC、
  以及 Realtime 推送层重构

选 B 的话，隐私政策那段要跟着重写。
