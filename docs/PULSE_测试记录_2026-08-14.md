## 一、[已修] 等待方永远收不到匹配成功通知 —— 最严重

**现象**：Joe 先进队列，Claude 后进。Claude 立刻看到「It's a match!」，
Joe 的手机**一直停在倒计时 07:12**，而数据库里 Joe 3 分钟前就已经是 `matched`。

**根因**：`lib/api/match.ts` 的 `subscribeToMatchResult` 监听 `match_queue` 的
Realtime UPDATE 事件，但 `supabase_realtime` 发布里**只有 messages 和 friendships**
（迁移 30 建的）。`match_queue` 是迁移 60 才建的表，补发布这一步漏了。
数据库确实 UPDATE 了，但事件不推送给任何客户端。

**为什么一直没被发现**：两边路径不对称 ——
- 后发起方：`join_match` **同步返回** `{status:'matched', groupId}`，根本不走 Realtime
- 先等待方：只能靠 Realtime

单人自测时你永远是"后发起方"，一切正常。

**修复**：
- 迁移 68：`alter publication supabase_realtime add table public.match_queue`
- `TravelModeScreen`：等待期间每 3 秒轮询 `getMyMatchStatus()` 兜底（推送会因弱网/切后台/断线丢失）
- 回滚：`db-backups/2026-08-14/ROLLBACK_68.sql`

**验证**：反过来让 Claude 先等、Joe 后发起 —— 等待页自动关闭并弹出 It's a match ✅

## 二、[已修] 取消按钮"点不动"

`handleCancelMatch` 里 `setMatching(false)` 排在 `await cancelMatching()` **之后**，
网络请求没返回界面就一直卡着，用户以为按钮失灵。

改成**先关界面、请求后台发**。取消是纯善意操作，网络失败也不该把用户困在等待页。

## 三、[待修] `get_my_profile` 不返回 `pet_breed`

```sql
-- 云端实测
get_my_profile 返回 pet_stage：true
get_my_profile 返回 pet_breed：false   ← 缺失
```

`pet_breed` 是迁移 58 加的列，而 `get_my_profile` 是迁移 25 写的，**没跟着更新**。

**后果**：客户端凡是读 `profile.pet_breed` 的地方全部拿到 `undefined`，
退化到兜底值 `'dog'`：

- 匹配等待页给外星人宠物画了一只**狗**（实测截图为证：标题写着 "Zorp is looking…"，
  说明 `pet_name` 正常，只有 breed 丢了）
- `ProfileScreen` 的 `currentPetBreed`、Closet 里的形态预览
- `ChatScreen` 自己宠物头像的兜底分支

**注意**：zZuPer Talk 的 AI 人格**不受影响** —— `pet-chat` 函数自己会从数据库读 profile，
客户端传的 breed 只是覆盖值。所以猫依然会 `Nya~`，但**界面上画的是狗**。

修法：给 `get_my_profile` 补一列。属于读取契约，不涉及 Ethan 的代码。

## 五、[Ethan] AI 对聊的自动轮转从未触发过

**实测证据**：两次匹配产生的会话，数据库里**都只有 1 条消息**
（发起方宠物的开场白，由 `join_match` 直接插入）。之后一条来回都没有。

**双重原因**：

1. **pg_net 扩展没安装**
   ```sql
   select count(*) from pg_extension where extname='pg_net';  →  0
   ```
   触发器 `trigger_agent_chat_reply` 靠 `net.http_post()` 戳 Edge Function，
   `net` schema 不存在 → 必然抛异常。而函数末尾是：
   ```sql
   exception when others then return new;   -- 静默吞掉
   ```
   **每次插消息触发器都在失败，没有任何日志或报错。**

2. **webhook 地址指向本地 Docker**
   ```sql
   select public.get_supabase_internal_url();
   →  http://kong:8000/functions/v1/agent-chat
   ```
   `kong:8000` 是 Supabase CLI 本地容器的网关，托管云端不存在这个主机。
   **就算装了 pg_net 也连不通。**

这意味着 Scheme C 那套设计精细的接管状态机（接管即停 / 缓冲一条 / 上限 15 条）
目前**一行都没有执行过**。

## 六、[Ethan] 外星人在摇尾巴

Zorp 是 **Quirky Alien（ENTP / roast master）**，开场白却是：

> *Strikes bold pose* Hey Joe! Let's embark on a **paw-some** adventure together!
> *High-five!* What's the next epic **chase** of the day? 🚀 ***Wags tail** enthusiastically!*

**根因**在 `getPetStageConfig`：阶段指令是**品种无关**的，而且写得非常具体
（直接给了动作清单 `*high-five!*, *fist bump!*, *strikes bold pose*`），
品种那边只贡献一句 `unconventional roast master`。**阶段压倒品种。**

**对比 `pet-chat`**：那边猫会说 `Nya~ Purrrrr~`，品种特征很强，而且明令禁止星号动作。
**同一套宠物系统，两个函数的输出规则相反、表现完全不一致。**

## 八、[已更正] 关于 0.2 阈值 —— 我最初的判断是错的

> **原文写的是**：「阈值形同虚设，两段随便的英文文本相似度通常就在 0.2–0.5，
> 这个门槛几乎总是通过。」
>
> **这个结论已被同日的 Roam 实测推翻**（见 `ROAM_测试记录_2026-08-14.md` 第四条）：
> 两段无关短文本的真实余弦相似度只有 **0.1113**，远低于 0.2。
> **阈值是实打实在拦人的**，不是摆设。

修正后的事实：

- **Pulse（`try_match_user`）**：阈值确实常常拦不住人，但**不是因为阈值低**，
  而是因为它**有兜底** —— 没有超阈值候选就配「等最久」的，完全不看相似度。
  所以人少时 Pulse ≈ 先到先配，这是兜底逻辑的效果，不是阈值的效果。

- **Roam（`match_travel_posts`）**：**没有兜底**，过不了 0.2 就是空列表。
  实测两条真实漂流互相刷不到，就是被这个门槛拦下的。

**教训**：这条我当初是凭对 embedding 相似度分布的经验判断写的，没有实测。
涉及具体数值的结论必须用真实数据验证 —— 尤其是"这个东西没用"这种否定性判断。
