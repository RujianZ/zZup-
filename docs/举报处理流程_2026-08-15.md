# 举报处理流程

> **为什么必须有这份文档**：`terms.html`、`guidelines.html`、`safety.html` 三处
> 都白纸黑字写了「24 小时内处理举报」。功能已经上线、通知已经能响，
> 但**收到之后谁处理、怎么处理没有定** —— 没有流程，那三句话就是不实陈述，
> 而 Apple 指南 1.2 要求的正是「24 小时内处理并移除违规者」。
>
> 这份是给 Joe 和 Ethan 两个人用的操作手册，不是给用户看的。

---

## 一、举报是怎么到你手上的

```
用户提交 → reports 表 → 触发器 → ops-notify Edge Function → Discord #ops 频道
```

Discord 消息按类目着色：

| 颜色 | 含义 |
|---|---|
| 🔴 红 + `@here` | `underage`（未成年）或 `self_harm`（自伤） |
| 🟠 橙 | 其余所有举报 |

**红色的必须优先，而且有法律义务**，见第四节。

---

## 二、在哪看完整举报

`reports` 表**没有任何 SELECT 策略**，客户端一律读不到（这是有意的：能读回自己的举报
就等于能反查某个宠物马甲背后是谁）。只能从 Supabase Dashboard 用 service_role 看：

```sql
select
  id, created_at, status,
  category, description,
  reporter_zzup_id, reported_zzup_id, reported_identity,
  context ->> 'reported_alias'          as 被举报宠物的会话代号,
  context ->  'conversation_id'         as 会话,
  jsonb_array_length(context -> 'messages') as 快照条数,
  attachments
from public.reports
where status = 'open'
order by
  (category in ('underage','self_harm')) desc,   -- 危及人身的排最前
  created_at asc;                                 -- 其余先到先办
```

**看会话快照**（提交时自动抓的最近 50 条）：

```sql
select jsonb_pretty(context -> 'messages') from public.reports where id = '<举报 id>';
```

**看截图**：`attachments` 里是 `report-media` 私有桶的路径，
在 Dashboard → Storage → report-media 里按路径找，或生成签名 URL。

## 三、24 小时怎么保证

**当前只有两个人，所以规则要简单到不会忘。**

| | |
|---|---|
| 主责 | Joe |
| 备份 | Ethan（Joe 24 小时内没响应时） |
| 检查频率 | 每天至少一次；红色 `@here` 立即 |
| 时区 | 一律按**美东**算（与年龄门槛一致，见迁移 75） |

在 Discord 频道里**用回复标记认领**，避免两个人重复处理或都以为对方在处理。

> ⚠️ 用户量上来之后这套人肉流程会先崩。届时需要的是一个后台页面
> （能看列表、看快照、一键处置），而不是更勤快地刷 Discord。

## 四、处置分级

处置动作目前**没有界面，全部是手工 SQL**。这是已知的临时状态。

### 🔴 立即处理（红色通知）

**`underage`（涉未成年）/ `self_harm`（自伤）**

1. **先看内容，不要先删** —— 见第五节的保存义务
2. `self_harm`：如果是求助信号，考虑推送危机资源（988 Suicide & Crisis Lifeline）。
   ⚠️ 这块要跟 Ethan 协调 —— 宠物 AI 的危机应答协议在他那边，
   而且**云端 `pet-chat` 至今没有部署他写好的那版**（见待办清单第八节）
3. `underage`：若确认举报对象未满 18 岁 → 封禁账号。年龄门槛是注册时的中立声明
   （迁移 75），谎报年龄拦不住，事后处置是唯一手段
4. 若涉及 CSAM → **立刻停止自行处置**，走第五节

### 🟠 常规

| 类目 | 一般处置 |
|---|---|
| `harassment` / `violence` | 一次警告；重复或严重 → 封禁 |
| `sexual_content` | 移除内容 + 警告；对未成年人发送 → 直接封禁 |
| `spam` / `impersonation` | 移除内容；重复 → 封禁 |
| `other` | 逐条判断 |

### 手工处置 SQL

```sql
-- 结案（actioned = 采取了措施；dismissed = 查证后不属实）
update public.reports
   set status = 'actioned',
       handled_by = '<你的 profiles.id>',
       handled_at = now(),
       resolution_note = '警告已发出'
 where id = '<举报 id>';

-- 封禁：目前**没有封禁机制**。当前唯一手段是软删除该账号，
-- 这会抹除 PII 但保留消息（见迁移 67）。
-- ⚠️ 这是个缺口：软删除是「用户自己删号」的语义，不是「平台封禁」。
--    真正的封禁需要一个 banned_at 字段 + 登录拦截。见下方「已知缺口」。
```

## 五、法律保存义务（涉未成年人内容）

**18 U.S.C. § 2258A** 和 **2024 REPORT Act** 要求：涉未成年人性剥削内容
必须向 NCMEC 报告，且相关材料**保存至少 1 年**。

所以：

- **不要删除** `reports` 行、会话消息、或 `report-media` 里的截图
- 这也是临时会话到期改成**冻结而非删除**的原因（迁移 82）——
  会话没了，举报快照就是空的
- 确认涉 CSAM 时：向 NCMEC CyberTipline 报告（https://report.cybertip.org），
  并保留全部原始材料

## 六、已知缺口（这份流程还不完整的地方）

| 缺口 | 影响 |
|---|---|
| **没有封禁机制** | 只能软删除账号，语义是「用户自己删号」不是「平台封禁」。需要 `banned_at` + 登录拦截 |
| **没有内容过滤** | Apple 1.2 五项要求里唯一完全空着的一项。若用 LLM 审核，属 Ethan 的领域，需先协调 |
| **没有后台界面** | 全部靠 Supabase Dashboard 手敲 SQL |
| **没有申诉流程** | `terms.html` 里留着 `[Define appeal SLA.]` 占位符未填 |
| **举报人拿不到结果** | 有意为之（读回举报会泄露马甲身份），但用户体验上是个黑洞 |
